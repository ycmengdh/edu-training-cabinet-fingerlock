# ESP32指纹锁实训柜权限管理系统 - 功能与方案文档

> **文档版本：V3.0** | 更新日期：2026-07-14

## 1. 项目概述

### 1.1 项目背景

本项目是针对学校实训场景设计的实训柜指纹权限管理系统。每个实训柜配备一个ESP32模块和指纹模块组成的指纹锁，通过WiFi与上位机进行通信，实现指纹权限的远程管理和分配。

### 1.2 项目目标

- 实现基于指纹识别的实训柜门锁控制
- 建立三级权限管理体系（系统管理员/老师/学生）
- 支持远程权限分配和管理
- 确保系统安全性和可靠性

### 1.3 应用场景

学校实训室中，每个实训柜配备一套指纹锁系统，学生和老师通过指纹识别打开对应的柜门，系统管理员负责整体权限管理。

## 3. 权限管理方案

### 3.1 权限等级定义

| 权限等级 | 角色名称 | 权限描述 | 系统锁权限 |
| :--- | :--- | :--- | :--- |
| Level 1 | 系统管理员 | 可开启所有4个锁 | **有** |
| Level 2 | 老师 | 可开启除系统锁外的所有锁 | **无**（默认） |
| Level 3 | 学生 | 由老师分配指定锁的权限 | **无**（默认） |

**补充说明**：

- 学生不可登录上位机后台（仅管理员和老师可登录后台管理系统）
- 管理员默认拥有最高权限，可管理所有班级、用户和设备
- 老师只能管理自己负责的班级及其学生，不能跨班级操作（录入/指纹/柜子分配/权限分配均限于本班）
- 学生权限由所属班级的负责老师分配，老师本人权限由管理员分配

### 3.2 锁编号规则

| 锁编号 | 锁名称 | 说明 |
| :--- | :--- | :--- |
| Lock 0 | 系统锁 | 仅系统管理员可开启 |
| Lock 1 | 实训柜1 | 老师和授权学生可开启 |
| Lock 2 | 实训柜2 | 老师和授权学生可开启 |
| Lock 3 | 实训柜3 | 老师和授权学生可开启 |

### 3.3 权限矩阵

| 角色 | Lock 0 (系统锁) | Lock 1 | Lock 2 | Lock 3 |
| :--- | :--- | :--- | :--- | :--- |
| 系统管理员 | ✅ | ✅ | ✅ | ✅ |
| 老师 | ❌ | ✅ | ✅ | ✅ |
| 学生（未授权） | ❌ | ❌ | ❌ | ❌ |
| 学生（授权Lock1） | ❌ | ✅ | ❌ | ❌ |
| 学生（授权Lock1+Lock2） | ❌ | ✅ | ✅ | ❌ |

## 4. 系统架构设计

### 4.0 ESP-MESH 自组网方案

#### 4.0.1 组网问题分析

当系统部署40个柜子（40台ESP32设备）时，传统WiFi路由器方案面临以下痛点：
- 需要部署企业级路由器/AP，且要求其能稳定承载40+客户端并发
- 每台ESP32都需要预先配置 WiFi SSID/密码、上位机IP/端口
- 路由器成为单点故障：路由器宕机整个系统瘫痪
- 实训柜金属外壳对WiFi信号衰减严重，单个AP覆盖可能不足
- 一旦换场地或换路由器，40台设备全部需要重新配网

#### 4.0.2 组网方案对比

| 方案 | 描述 | 优点 | 缺点 | 推荐度 |
| :--- | :--- | :--- | :--- | :--- |
| **方案A：路由器组网** | 部署路由器，所有ESP32作为客户端连接 | 实时通信、协议成熟 | 需路由器基础设施、配网繁琐、单点故障 | ★★★☆☆ |
| **方案B：ESP32开热点** | ESP32开AP热点，上位机逐个连接 | 无需路由器 | 不可扩展、无法实时管理40台 | ★☆☆☆☆ |
| **方案C：ESP-MESH自组网** | 40台ESP32自动组树状Mesh，根节点USB串口接上位机 | **零路由器、零配网、自动修复、单点接入** | 单跳延迟略增（可接受） | **★★★★★** |

#### 4.0.3 推荐方案：ESP-MESH 自组网 + USB串口桥接

**核心思想**：40台ESP32通过乐鑫官方 ESP-MESH 协议自动组成树状网络，其中**1台作为根节点（Root）**通过USB串口直连上位机。所有设备间通信走Mesh，根节点负责 Mesh ↔ 串口 双向转发。

#### 4.0.4 ESP-MESH 协议说明

**ESP-MESH** 是乐鑫官方为ESP32推出的WiFi Mesh协议（组件名 `esp_mesh`），特点：

| 特性 | 说明 |
| :--- | :--- |
| 拓扑结构 | 树状（也支持链状），自动维护父子关系 |
| 节点容量 | 官方标称支持数十至数百节点，40台设备完全在能力范围内 |
| 自组网 | 上电自动扫描、自动选举根节点、自动加入网络 |
| 自修复 | 任一节点掉线，子节点自动重新寻找父节点接入 |
| 通信方式 | 节点间通过Mesh层收发数据包，无需TCP连接 |
| 传输层 | 应用层 JSON 消息直接走Mesh数据包，无需TCP/UDP |
| 安全性 | 支持Mesh密码（AES加密），防止未授权节点加入 |
| 兼容硬件 | ESP32-WROOM-32 原生支持，无需额外模块 |

**树状拓扑示意（40节点典型结构）**：

```
                    [Root] ESP32#1 ◄─── USB串口 ───► 上位机
                   /      |      \
                  /       |       \
            [Node#2]  [Node#3]  [Node#4]
            /   \       |        /   \
       [Node#5][#6]  [Node#7][#8][#9]
          ...           ...        ...
        叶子层：约30+个节点
```

- 根节点：1台，固定为ESP32#1（可通过配置或自动选举）
- 中间节点：约6-10台，承担数据转发
- 叶子节点：约30台，只收发自己业务数据
- 推荐拓扑深度：3-4层（避免过深增加延迟）

#### 4.0.5 节点角色定义

| 节点角色 | 数量 | 硬件 | 职责 | 与上位机通讯 |
| :--- | :--- | :--- | :--- | :--- |
| **根节点 (Root)** | 1台 | ESP32 + USB线 | Mesh根 + 串口桥接 | USB串口直连 |
| **普通节点 (Node)** | 39台 | ESP32 | 指纹锁控制 + Mesh通讯 | 经Mesh路由到Root |

**根节点特殊处理**：
1. Mesh启动时设置为 `MESH_ROOT`（或开启自动选举，配置最高优先级）
2. 启用USB CDC虚拟串口（或UART0），与PC通讯
3. 在Mesh层与串口之间双向转发JSON消息包
4. 根节点本身也可以连接指纹锁（即可兼作1号实训柜）

**普通节点行为**：
1. Mesh启动时设置为 `MESH_NODE`，自动寻找父节点
2. 收到指纹/按键事件，通过 `esp_mesh_send()` 发往根节点
3. 监听Mesh层接收，处理上位机下发的命令
4. 与原TCP方案完全使用相同的消息格式（`Message` 结构不变）

#### 4.0.6 节点身份与设备编号映射

每个ESP32在Mesh网络中拥有两类身份：

| 身份类型 | 标识 | 用途 | 获取方式 |
| :--- | :--- | :--- | :--- |
| **Mesh Layer Address** | 6字节MAC | Mesh内部路由 | 启动时自动获取 |
| **Device ID** | 字符串（如 `CABINET_001`） | 业务层标识 | Flash预存 |

**上位机识别设备流程**：
1. ESP32上电组网成功后，向Root发送 `REGISTER` 消息（含 `device_id` 和 `device_name`）
2. Root转发到串口给上位机
3. 上位机记录 `device_id` ↔ Mesh MAC 映射
4. 后续命令通过 `device_id` 路由（Root内部维护 `device_id` → Mesh MAC 表）

#### 4.0.7 USB串口桥接设计

**串口参数**：

| 项目 | 值 | 说明 |
| :--- | :--- | :--- |
| 物理接口 | USB Type-C/Micro-USB | ESP32原生USB或CH340/CP2102 |
| 虚拟串口 | CDC (USB CDC) 或 UART0 | 优先用USB CDC，无需额外芯片 |
| 波特率 | `921600` bps | 高波特率降低传输延迟 |
| 数据位 | 8 / 无校验 / 停止位1 | 标准配置 |
| 流控 | 无 | 简化接线 |
| 消息分隔 | `\n` 换行符 | 与原TCP协议一致 |
| 数据格式 | JSON + `\n` | 与原TCP协议完全一致 |

**根节点串口桥接逻辑**：

```c
// mesh_bridge.cpp (根节点专用)
// Mesh层 → 串口：转发所有子节点上报的消息到PC
void onMeshReceive(const mesh_addr_t *from, const mesh_data_t *data) {
    // data->data 是 JSON 字符串
    Serial.write(data->data, data->size);
    Serial.write('\n');
}

// 串口 → Mesh层：把PC下发的命令按 device_id 路由到对应子节点
void onSerialReceive(const String &line) {
    Message msg = Message::parse(line);
    mesh_addr_t target = lookupDeviceId(msg.device_id);  // 查MAC表
    mesh_data_t data = { (uint8_t*)line.c_str(), line.length()+1, 0 };
    esp_mesh_send(&target, &data, MESH_DATA_P2P, NULL, 0);
}
```

#### 4.0.8 双模式保留（Mesh模式 + 调试模式）

为兼顾日常使用与单台调试，ESP32保留两种工作模式，通过按键切换：

| 模式 | 名称 | 触发条件 | 用途 | 通讯方式 |
| :--- | :--- | :--- | :--- | :--- |
| **Mesh模式** | 默认 | 上电默认 | 40台集中部署 | ESP-MESH + USB串口(Root) |
| **调试模式** | AP模式 | 长按按键10秒切换 | 单台调试/无Mesh环境 | ESP32开AP热点 + TCP |

**模式切换**：
- 长按4个按键中任意1个保持10秒
- ESP32重启并切换到另一种模式
- LED指示当前模式：Mesh模式慢闪 / 调试模式快闪

> 调试模式保留原 AP+TCP 方案，便于在没有Mesh网络的情况下对单台设备进行指纹录入、参数配置等操作。日常部署统一使用Mesh模式。

#### 4.0.9 上位机Mesh桥接设计

上位机将原 TCP 监听逻辑替换为 **USB串口桥接**，业务层完全不变：

```csharp
// Network/MeshBridge.cs  (替换原 TcpServer.cs)
// 通过USB串口与Mesh根节点通讯，管理40台ESP32
public class MeshBridge
{
    private SerialPort _port;
    private readonly Dictionary<string, DeviceClient> _devices = new();
    
    // 启动串口连接根节点
    public void Start(string portName = "COM3", int baudRate = 921600)
    {
        _port = new SerialPort(portName, baudRate);
        _port.DataReceived += OnSerialData;
        _port.Open();
        Console.WriteLine($"[Mesh] 已连接根节点 {portName}@{baudRate}");
    }
    
    // 串口收到数据 → 按行解析 → 走原有 MessageHandler
    private void OnSerialData(object s, SerialDataReceivedEventArgs e)
    {
        while (_port.ReadLine() is { } line)
        {
            var msg = Message.FromJson(line);     // 复用原 Message 模型
            if (msg?.Cmd == Protocol.CmdRegister)
                _devices[msg.DeviceId] = new DeviceClient(msg.DeviceId);
            
            MessageHandler.Handle(msg);           // 复用原消息处理
        }
    }
    
    // 上位机 → 设备：写入串口，根节点内部按 device_id 路由
    public void Send(string deviceId, string cmd, object data)
    {
        var msg = Message.Create(cmd, deviceId, data);
        _port.Write(msg.ToJson());                // JSON + \n
    }
}
```

> **关键点**：业务层（`Services/*`、`MessageHandler`、`Models/*`）零改动，仅 `Network/` 层实现替换。原 TCP 方案的消息格式、命令枚举、JSON 结构完全保留。

#### 4.0.10 离线缓存与断网容错

虽然Mesh根节点USB直连PC可靠性高，仍保留离线容错能力：

| 故障场景 | 系统行为 |
| :--- | :--- |
| 某子节点掉线 | Mesh自动重路由，该节点业务中断但其他节点正常 |
| 根节点USB断开 | 上位机立即检测到，所有设备离线缓存日志，根节点恢复后批量同步 |
| 单节点与Mesh失联 | 本地缓存开锁日志（最多100条），网络恢复后批量上报 |
| 上位机软件关闭 | ESP32继续工作（权限已缓存），日志本地保存，PC重启后同步 |

#### 4.0.11 部署使用流程

**首次部署**：
1. 烧录固件到40台ESP32（统一固件，通过Flash配置区分Root/Node）
2. 设置1台为Root节点（写入 `is_root=true` 配置）
3. Root节点通过USB连接PC
4. 上电后40台ESP32自动组网（约30-60秒）
5. 上位机打开串口，自动识别40台设备注册消息

**日常使用**：
1. 上位机启动 → 自动连接Root串口
2. 40台ESP32上电 → 自动加入Mesh网络
3. 用户按指纹 → 设备Mesh发往Root → Root串口转PC → PC验证后回传
4. 日志实时上传，权限变更实时下发

**新增/更换设备**：
1. 烧录相同固件，配置 `device_id`
2. 上电即可自动加入Mesh网络（无需任何配网操作）

**场地迁移**：
- 整体打包40台ESP32 + 1根USB线 + 1台PC
- 无需重新配网，上电自动组网

#### 4.0.12 硬件部署建议

**Root节点位置**：
- 放置在实训室中央位置，确保Mesh无线覆盖良好
- 通过USB延长线连接到上位机PC
- 单独供电（USB供电或独立5V电源）

**子节点布局**：
- 每台ESP32安装在实训柜内部，外接天线引出柜体（如信号衰减严重）
- 避免金属柜体完全封闭ESP32天线
- 相邻实训柜间距建议 < 10米（Mesh单跳可靠距离）

**Mesh网络优化**：
- 拓扑深度建议 ≤ 4 层
- 中间层节点选择信号好的位置（自动选举优先信号强度）
- 必要时增加1-2台纯转发节点（不接指纹锁，仅作Mesh中继）

#### 4.2.3 ESP32 Flash 存储设计

ESP32-WROOM-32 Flash 总容量 4MB，需存放固件、配置、权限、日志、指纹模板等数据。Flash 寿命有限（每扇区约 10万次擦写），需合理分区与磨损均衡。

##### Flash 分区规划（4MB Flash）

```
┌─────────────┬──────────┬──────────────────────────────┐
│ 分区名      │ 偏移     │ 大小      │ 用途              │
├─────────────┼──────────┼───────────┼──────────────────┤
│ bootloader  │ 0x1000   │ 0x7000    │ 引导程序          │
│ partitions  │ 0x8000   │ 0x1000    │ 分区表            │
│ app0        │ 0x10000  │ 0x180000  │ 应用固件(1.5MB)   │
│ app1(OTA)   │ 0x190000 │ 0x180000  │ OTA备份(1.5MB)    │
│ nvs         │ 0x310000 │ 0x4000    │ NVS键值存储(16KB)│
│ perm_store  │ 0x314000 │ 0x20000   │ 权限数据(128KB)   │
│ log_store   │ 0x334000 │ 0x20000   │ 离线日志(128KB)   │
│ config      │ 0x354000 │ 0x4000    │ 设备配置(16KB)    │
│ fp_template │ 0x358000 │ 0x60000   │ 指纹模板备份(384KB)│
│ reserved    │ 0x3B8000 │ 0x48000   │ 预留              │
└─────────────┴──────────┴───────────┴──────────────────┘
```

##### 存储技术选型

| 数据类型 | 存储方式 | 理由 |
| :--- | :--- | :--- |
| 设备配置(NVS) | **NVS(非易失性存储库)** | 乐鑫官方组件,自带磨损均衡+键值API |
| 权限数据 | **NVS Blob** | 量小(<64KB),频繁读、低频写,NVS足够 |
| 离线日志 | **环形缓冲(自定义)** | 频繁写,NVS的"擦写后写"不适合,自实现磨损均衡 |
| 指纹模板 | **AS608模块自带Flash** | 模板存在AS608内部Flash,ESP32仅存索引 |
| 设备列表(Root用) | **NVS Blob** | 量小,低频写 |

##### 权限数据存储格式（紧凑二进制）

为节省 Flash 空间，权限数据采用紧凑二进制而非 JSON 存储：

```
权限数据文件结构（perm_store 分区内,通过NVS Blob存取）：
┌────────────────┬─────────────────────────────────────┐
│ 文件头 (16B)   │ 权限版本(4B) + 用户数(2B) +          │
│                │ 保留(2B) + CRC32(4B) + 魔数(4B)     │
├────────────────┼─────────────────────────────────────┤
│ 用户记录数组   │ 每条记录 12B,见下表                  │
└────────────────┴─────────────────────────────────────┘

单条用户记录(12B):
┌──────────────┬──────────┬──────────┬───────────┬──────────────┐
│ fingerprint_id│ user_id  │ lock_perm│ role      │ expire_days  │
│ 2B           │ 4B       │ 1B(bit0-3)│ 1B       │ 4B(距2000-01-01天数)│
└──────────────┴──────────┴──────────┴───────────┴──────────────┘
```

| 字段 | 长度 | 说明 |
| :--- | :--- | :--- |
| fingerprint_id | 2B | AS608指纹ID(1-30000) |
| user_id | 4B | 上位机用户ID(数字形式,够用) |
| lock_perm | 1B | 4个锁权限,bit0-3分别对应Lock0-3 |
| role | 1B | 0=admin 1=teacher 2=student |
| expire_days | 4B | 过期天数(距2000-01-01),0xFFFFFFFF表示永久 |

##### 容量评估

| 项目 | 单条大小 | 数量上限 | 总占用 |
| :--- | :--- | :--- | :--- |
| 用户权限记录 | 12B | 200用户 | 2.4KB |
| 文件头 | 16B | - | 16B |
| **权限数据总计** | - | - | **≈2.5KB**(远小于128KB分区) |

> 即使扩展到 1000 用户，权限数据仅 12KB，Flash 完全够用。权限分区预留 128KB 是为了写入磨损均衡（NVS内部使用）。

##### 离线日志存储（环形缓冲）

权限数据通过 NVS 存储，但离线日志写入频繁（每次开锁一条），不适合 NVS 的"擦-写"模式，自定义环形缓冲：

```
log_store分区(128KB = 32个4KB扇区):
┌──────┬──────┬──────┬──────┬─────┬──────┐
│扇区0 │扇区1 │扇区2 │扇区3 │ ... │扇区31│
└──────┴──────┴──────┴──────┴─────┴──────┘
   │      │      │      │             │
   │      │      │      │             └─写指针当前指向
   │      │      │      └─已写满
   │      │      └─已写满
   │      └─已写满
   └─起始
```

**单条日志记录(32B)**：
```
┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────────┐
│ log_seq  │ user_id  │ fp_id    │ lock_id  │ result   │ timestamp    │
│ 4B       │ 4B       │ 2B       │ 1B       │ 1B       │ 4B(unix时间) │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────────┘
+ 16B预留(可扩展存reason等)
```

- 单扇区(4KB)可存 128 条日志
- 总容量 32×128 = **4096 条日志**
- 按每天100条估算，可缓存约 40 天
- 写满后自动覆盖最旧扇区（环形）

**磨损均衡**：写入按扇区顺序轮转，写满一扇区才擦下一扇区。每扇区寿命10万次，32扇区可承受 320万次擦写，按每天100条日志估算可使用 **800+年**。

##### 数据完整性保障

| 风险 | 措施 |
| :--- | :--- |
| 写入中途断电 | 双区写入(A/B两份),写完一份再擦另一份,任一份CRC通过即用 |
| Flash位翻转 | 每份末尾存CRC32,启动时校验,失败回退另一份 |
| 跨分区误写 | 分区头加魔数(0xA5A55A5A),校验魔数才认为有效 |
| NVS损坏 | NVS自带磨损均衡+加密校验,损坏时整体重置并请求上位机全量同步 |
| 权限数据丢失 | 启动时CRC失败→向Root上报PERM_LOST→上位机自动全量同步 |

##### 启动加载流程

```
ESP32上电
   │
   ▼
读取perm_store的A区 ──► CRC校验
   │                      │
   │                   ┌──┴──┐
   │                   │通过 │失败
   │                   ▼     ▼
   │              使用A区  读B区CRC校验
   │                   │     │
   │                   │  ┌──┴──┐
   │                   │  │通过 │失败
   │                   │  ▼     ▼
   │                   │ 使用B区 权限为空
   │                   │        │
   └───────────────────┴────────┴──► 加入Mesh
                                       │
                                       ▼
                            上报REGISTER + 当前权限版本号
                                       │
                                       ▼
                            上位机比对版本号,不一致则SYNC_PERMISSIONS全量同步
```

## 5. 通信协议设计

### 5.1 通信方式

V2.0 方案采用 **ESP-MESH + USB串口** 双段通讯链路：

| 链路段 | 协议 | 介质 | 说明 |
| :--- | :--- | :--- | :--- |
| **设备 ↔ 根节点** | ESP-MESH (P2P) | WiFi 2.4G | 40台ESP32自组网，应用层JSON直接走Mesh数据包 |
| **根节点 ↔ 上位机** | USB CDC 虚拟串口 | USB | 921600 bps，JSON + `\n` 分隔 |

**关键特性**：
- 应用层消息格式与V1.0 TCP方案**完全一致**（JSON + `\n`）
- 业务层无需感知底层是TCP还是Mesh，仅Root做协议转换
- 调试模式（AP+TCP）保留作为单台设备维护通道

### 5.2 数据格式

采用JSON格式进行数据传输，每个数据包包含以下字段：

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `cmd` | string | 命令类型 |
| `device_id` | string | 设备唯一标识（业务层路由依据） |
| `data` | object | 数据内容 |
| `timestamp` | string | 时间戳 |
| `checksum` | string | 校验和（可选） |

**消息封装链路**：

```
[业务层]    JSON 字符串 + \n
   │
   ▼
[ESP32子节点] esp_mesh_send(root, json_bytes)  ───►  [Root]  ───► Serial.write(json+\n)
                                                                  │
                                                                  ▼
[上位机业务层] JSON 字符串 + \n  ◄─── SerialPort.ReadLine()  ◄─── [PC串口]
```

### 5.3 命令列表

#### 5.3.1 下位机 → 上位机

> 以下命令通过 Mesh 上报到 Root，Root 透传到串口给上位机。"模式"列表示典型使用场景。

| 命令 | 说明 | 典型模式 | 数据结构 |
| :--- | :--- | :--- | :--- |
| `REGISTER` | 设备注册（含Mesh MAC） | Mesh | `{"device_name": "实训柜1", "mesh_mac": "A4:CF:12:..."}` |
| `FINGER_VERIFY` | 指纹验证请求 | 两者 | `{"fingerprint_id": 1}` |
| `STATUS_REPORT` | 状态上报 | Mesh | `{"online": true, "lock_status": [0, 0, 0, 0]}` |
| `LOG_REPORT` | 日志上报 | 两者 | `{"user_id": "U001", "lock_id": 1, "action": "open", "time": "2024-01-01 00:00:00"}` |
| `CONFIG_RESPONSE` | 配置读取响应 | 两者 | `{"device_id": "...", "wifi_ssid": "...", "server_ip": "...", ...}` |
| `STATUS_RESPONSE` | 状态读取响应 | 两者 | `{"uptime": 3600, "lock_status": [0,0,0,0], "log_count": 15}` |
| `CONFIG_SAVED` | 配置保存成功 | 两者 | `{"result": "success"}` |

#### 5.3.2 上位机 → 下位机

> 以下命令通过串口下发给 Root，Root 根据 `device_id` 查Mesh MAC表后 `esp_mesh_send` 到目标节点。

| 命令 | 说明 | 典型模式 | 数据结构 |
| :--- | :--- | :--- | :--- |

### 5.5 消息帧格式设计

为保证 Mesh 数据包与 USB 串口传输的可靠性，定义统一的二进制帧格式。JSON 文本作为 payload 封装在帧内。

#### 5.5.1 帧结构

```
┌──────────┬──────────┬──────────┬─────────────────────┬──────────┐
│ 帧头     │ 版本     │ 负载长度 │  Payload (JSON)     │ CRC16    │
│ 0xA5 0x5A│ 1 byte   │ 2 byte   │  N byte (≤1400)     │ 2 byte   │
└──────────┴──────────┴──────────┴─────────────────────┴──────────┘
   2B         1B         2B           N B                  2B
```

| 字段 | 长度 | 说明 |
| :--- | :--- | :--- |
| 帧头 | 2B | 固定 `0xA5 0x5A`，用于接收端同步 |
| 版本 | 1B | 协议版本号，当前 `0x01`，便于未来升级 |
| 负载长度 | 2B | Payload 字节数（大端序），最大 1400B（ESP-MESH 单包上限） |
| Payload | N B | JSON 文本（UTF-8编码，**不含**末尾 `\n`） |
| CRC16 | 2B | 对"版本+长度+Payload"做 CRC-16/MODBUS 校验 |

> **说明**：原 V1.0 的"JSON + \n"分隔符方案在 USB 串口下仍可保留作为调试用，正式通信使用本帧格式。两种方案通过版本号区分。

#### 5.5.2 CRC16 校验

- 算法：CRC-16/MODBUS（多项式 0xA001）
- 计算范围：版本字段 + 长度字段 + Payload（不含帧头和 CRC 字段本身）
- 接收端校验失败：丢弃该帧，统计 `crc_error_count`，不上报应用层

```c
// ESP32 端 CRC16 计算（MODBUS多项式）
uint16_t crc16(const uint8_t *data, size_t len) {
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < len; i++) {
        crc ^= data[i];
        for (int j = 0; j < 8; j++) {
            crc = (crc & 1) ? (crc >> 1) ^ 0xA001 : (crc >> 1);
        }
    }
    return crc;
}
```

#### 5.5.3 帧大小与 MTU 适配

| 链路 | MTU | 单帧最大 Payload | 超长消息处理 |
| :--- | :--- | :--- | :--- |
| ESP-MESH (P2P) | 1500B | **1400B** | 自动分片（见 5.5.4） |
| USB CDC 串口 | 无限制 | 不限 | 不分片，直接发 |
| TCP (WiFi链路) | 1500B | 1400B | 自动分片 |

#### 5.5.4 大消息分片机制

当 Payload > 1400B（如 `SYNC_PERMISSIONS` 一次同步40用户权限），启用分片：

```
分片头（4B，加在 Payload 前面）：
┌──────────┬──────────┬──────────┐
│ 消息ID   │ 分片序号 │ 总分片数 │
│ 1B       │ 1B       │ 1B       │
└──────────┴──────────┴──────────┘
（保留1字节用于未来扩展）
```

- 接收端按 `消息ID` 缓存分片，收齐后拼接、校验、上报应用层
- 超时未收齐（5秒）：丢弃已收分片，请求重发

### 5.7 交互时序与流控机制

#### 5.7.1 请求-响应超时

| 命令类型 | 超时时间 | 失败重试次数 | 说明 |
| :--- | :--- | :--- | :--- |
| FINGER_VERIFY → AUTH_OK/FAIL | 2秒 | 2次 | 影响用户体验,超时短 |
| CONTROL_LOCK → 确认 | 1秒 | 1次 | 锁动作需快速响应 |
| ADD_FINGERPRINT → 确认 | 10秒 | 0次 | 涉及指纹采集,不可重试 |
| SYNC_PERMISSIONS → 确认 | 30秒 | 2次 | 大数据量,允许较长 |
| READ_CONFIG → CONFIG_RESPONSE | 3秒 | 2次 | 常规查询 |
| WRITE_CONFIG → CONFIG_SAVED | 5秒 | 1次 | 涉及Flash写入 |
| LOG_REPORT → 确认(ACK) | 3秒 | 3次 | 日志不可丢,重试多 |
| HEARTBEAT → 无需响应 | - | - | 单向保活 |

#### 5.7.2 ACK 确认机制

对于不可丢失的下行命令（`SYNC_PERMISSIONS` / `ADD_FINGERPRINT` / `WRITE_CONFIG` / `CONTROL_LOCK`），下位机处理后需回 ACK：

```json
{
  "cmd": "ACK",
  "device_id": "CABINET_001",
  "data": {
    "original_cmd": "SYNC_PERMISSIONS",
    "original_msg_id": "M20260712001",
    "result": "success",      // success/fail
    "error_code": 0,
    "error_msg": ""
  }
}
```

> 每条命令携带 `msg_id`（上位机生成,格式 `M+yyyyMMdd+序号`），下位机 ACK 时原样回传。

#### 5.7.3 重传策略

```
发送命令(msg_id=X) ──► 等待ACK(超时T)
                          │
              ┌───────────┴───────────┐
              │ 收到ACK(X)            │ 超时未收到
              ▼                       ▼
           完成                  重试次数+1
                                ┌─────┴─────┐
                                │ < 最大次数 │ ≥ 最大次数
                                ▼           ▼
                            重发命令(X)   标记失败,上报错误
```

#### 5.7.4 心跳与连接保活

- **上位机 → Root**：每 30 秒发一次 `HEARTBEAT`，连续 3 次无响应判定链路断开
- **Root → 子节点**：Mesh层自带保活，应用层每 60 秒轮询一次状态（`READ_STATUS`）
- **子节点 → Root**：每 60 秒主动上报 `STATUS_REPORT`

#### 5.7.5 流控与拥塞避免

- **单设备消息限速**：下位机同一时刻只允许 1 条未确认命令在途，避免 Mesh 拥塞
- **批量操作错峰**：上位机批量同步权限时，每台设备间隔 200ms 发送，避免 Mesh 风暴
- **日志批量上报**：下位机本地缓存日志，每 10 秒批量上报一次（最多 20 条），而非逐条上报
- **断网重连退避**：Mesh 失联后重连采用指数退避（5s/10s/20s/40s/60s 封顶）

## 6. 数据存储方案

### 6.0 整体存储架构

V3.0 重构后采用"根节点 SD 卡（业务主数据唯一持久化源） + 上位机 SQLite（运行数据） + 上位机备份目录"的混合存储架构，替代 V2.3 的 SQLite + FreeSql 单一方案。

| 存储位置 | 角色 | 内容 | 技术方案 |
| :--- | :--- | :--- | :--- |
| **根节点 SD 卡** | 业务主数据唯一持久化源 | 7 张 JSON 表 | DataStore 内存加载 + 文件读写 |
| **上位机 SQLite** | 运行数据本地存储 | logs / deploy_tasks / deploy_statuses / backup_records | Microsoft.Data.Sqlite |
| **上位机备份目录** | 操作前自动备份 | 7 张 SD 卡表 JSON 快照 zip | ./Backups/ |

**设计原则**：

- 业务主数据（用户/班级/权限/设备授权/指纹模板）以根节点 SD 卡为唯一权威源，上位机不另存业务副本
- 开锁日志、下发状态等运行数据走上位机本地 SQLite，便于查询和统计
- 所有系统用户操作前自动备份 SD 卡数据到上位机备份目录，确保可还原
- 上位机通过根节点 USB 串口读写 SD 卡 JSON 文件，根节点 DataStore 负责内存与文件同步

**架构示意**：

```
┌──────────────────┐   USB串口    ┌──────────────────────┐
│  上位机(PC)      │◄───────────►│  ESP32 根节点         │
│  C# / WPF        │  921600     │  (Mesh Root + SD卡)   │
├──────────────────┤             ├──────────────────────┤
│  - 业务逻辑      │             │  DataStore (内存)     │
│  - Microsoft.    │             │   ├ users.json        │
│    Data.Sqlite   │             │   ├ classes.json      │
│  - ./Data/       │  读写SD卡   │   ├ role_permissions │
│    system.db     │◄───────────►│   ├ user_permissions │
│  - ./Backups/    │             │   ├ device_auths.json │
│    *.zip         │             │   ├ devices.json      │
└──────────────────┘             │   └ fingerprint_tpl  │
                                 └──────────┬───────────┘
                                            │ ESP-MESH
                                  ┌─────────▼──────────┐
                                  │  40 台子节点        │
                                  │  (仅缓存下发权限)    │
                                  └────────────────────┘
```

- 详见 6.6 容量预警

### 6.5 下发链路

V3.0 区分老师和学生两类用户的下发策略，老师全量广播、学生按需下发。

#### 6.5.1 老师指纹广播下发

- 老师指纹录入完成后，系统自动向所有在线柜子广播下发（DEPLOY_USER 命令）
- 老师需在所有柜子都可开锁，因此指纹和权限全量广播
- 下发状态记录到 SQLite deploy_tasks + deploy_statuses

```
老师录入指纹 → 存根节点 SD卡 → 广播 DEPLOY_USER 到所有在线柜子
                                   │
                                   ▼
                         各柜子接收 → 写 AS608 Flash → ACK
                                   │
                                   ▼
                         上位机记录 deploy_statuses
```

#### 6.5.2 学生权限按需下发

- 学生权限不广播，仅在分配柜子+权限时才下发到对应柜子
- 下发命令：DEPLOY_USER（含用户信息+指纹模板+锁权限）
- 仅下发到 device_authorizations 中授权的柜子

```
学生分配柜子+权限 → 写 device_authorizations → DEPLOY_USER 到授权柜子
                                                    │
                                                    ▼
                                          目标柜子接收 → ACK
```

#### 6.5.3 下发状态追踪

- SQLite deploy_tasks 记录每次下发任务（任务ID、类型、目标数、成功/失败数）
- SQLite deploy_statuses 记录每台柜子的接收状态（pending/success/fail/timeout）
- 上位机界面可查看下发进度和失败明细

#### 6.5.4 手动重发机制

- 下发失败的柜子，可在界面手动触发重发
- 重发读取根节点 SD 卡最新数据，重新下发 DEPLOY_USER
- 重试次数记录在 deploy_statuses.retry_count

#### 6.5.5 事务性保障

- 下发成功才更新根节点 SD 卡 DeviceAuthorization
- 流程：先下发到柜子 → 收到 ACK → 写 device_authorizations.json → 返回成功
- 若下发失败，不写 SD 卡，保持原状态

```
分配权限 → 下发 DEPLOY_USER → 等待 ACK
                                │
                    ┌───────────┴───────────┐
                    │ 收到 ACK(success)      │ 超时/失败
                    ▼                       ▼
            写 device_authorizations    不写 SD卡，返回失败
            返回成功
```

### 6.6 容量预警

每台柜子 ESP32 Flash 容量有限，需监控指纹存储数量。

#### 6.6.1 容量限制参数

| 参数 | 值 | 说明 |
| :--- | :--- | :--- |
| PERM_MAX_USERS | 200 | 每台柜子最大用户数 |
| CAPACITY_WARN_THRESHOLD | 190 | 容量预警阈值（95%） |

#### 6.6.2 容量查询

- READ_CAPACITY 命令查询柜子已用/最大容量
- 返回数据：`{"used": 185, "max": 200, "warn": false}`
- 上位机定期轮询各柜子容量

#### 6.6.3 容量预警机制

- 柜子用户数达到 190（CAPACITY_WARN_THRESHOLD）时，上报预警
- 上位机界面高亮显示容量告警柜子
- 提示管理员执行清理操作（按班级删除归还空间）

#### 6.6.4 按班级删除归还空间

- 学生毕业时执行 DELETE_CLASS_USERS 命令
- 批量删除班级下所有学生在指定柜子的指纹和权限
- 归还 AS608 Flash 空间，释放容量
- 同时清理根节点 SD 卡对应记录

### 6.7 备份还原

V3.0 引入操作前自动备份机制，确保数据安全可还原。

#### 6.7.1 自动备份

- 每次系统用户操作前（新增/删除/修改用户、班级操作、权限变更、指纹录入等），自动备份
- 备份内容：7 张 SD 卡表的 JSON 快照打包为 zip
- 备份位置：`./Backups/backup_YYYYMMDD_HHmmss.zip`
- 备份记录写入 SQLite backup_records 表，便于追溯

#### 6.7.2 还原流程

1. 从 backup_records 选择备份点
2. 解压 zip → 取出 7 张 JSON 文件
3. 通过 USB 串口写回根节点 SD 卡（覆盖现有文件）
4. 通知根节点 DataStore 重新加载
5. 验证数据完整性

```
选择备份 → 解压 zip → 写回 SD卡 7 张 JSON → 重新加载 DataStore → 还原完成
```

#### 6.7.3 备份策略

- 数据以根节点 SD 卡为主，备份仅用于还原
- 备份不包含上位机 SQLite 数据（日志/下发状态可重建）
- 定期清理过期备份（默认保留最近 100 份）

### 6.8 指纹 4+2 录入流程

AS608 指纹模块要求 6 次按手指完成一枚指纹录入。

#### 6.8.1 录入步骤

| 步骤 | 操作 | 说明 |
| :--- | :--- | :--- |
| 1-4 | 采集图像 | 4 次采集指纹图像，生成特征 |
| 5-6 | 验证 | 2 次按手指验证指纹一致性 |

> 共 6 次按手指：4 次采集 + 2 次验证。中途失败需从头开始。

#### 6.8.2 录入流程

- 可在任意柜子录入（不限于根节点）
- 录入过程中，柜子通过 Mesh 上报采集进度到上位机
- 录入完成后，模板元数据存根节点 SD 卡 fingerprint_templates.json
- **本机不存储指纹模板**（模板下发时才写入目标柜子 AS608 Flash）

```
选择用户 → 选择录入柜子 → 提示按手指 ×4 → 生成特征 → 提示验证 ×2 → 录入成功
                                                                              │
                                                                              ▼
                                                 存根节点 SD卡 fingerprint_templates.json
                                                 （本机 AS608 不保留模板）
```

#### 6.8.3 老师录入后广播下发

- 老师指纹录入完成后，自动触发广播下发（详见 6.5.1）
- 将指纹模板下发到所有在线柜子
- 学生指纹不自动下发，待分配柜子时按需下发

### 6.9 10 秒开锁窗口

V3.0 优化开锁交互体验，验证通过后开放 10 秒开锁窗口。

#### 6.9.1 流程

1. 用户放手指 → 柜子 AS608 比对指纹 → 上报 FINGER_VERIFY
2. 上位机验证通过 → 回复 AUTH_OK，携带：
   - `window_seconds`: 10（开锁窗口时长）
   - `allowed_locks`: [false, true, false, true]（4 锁权限标记）
3. 柜子进入 10 秒开锁窗口：
   - 有权限的锁灯亮指示
   - 用户可按按钮开锁（仅能开有权限的锁）
   - 10 秒内可开多次
4. 窗口超时或按取消键 → 退出验证状态

#### 6.9.2 AUTH_OK 数据结构（V3.0 扩展）

```json
{
  "cmd": "AUTH_OK",
  "device_id": "CABINET_001",
  "data": {
    "user_id": "U001",
    "name": "张三",
    "role": "student",
    "fingerprint_id": 1,
    "window_seconds": 10,
    "allowed_locks": [false, true, false, true],
    "expire_time": "2026-08-12 00:00:00"
  }
}
```

> 相比 V2.3 的 `lock_permissions` 对象，V3.0 改用 `allowed_locks` 数组 + `window_seconds` 字段，支持 10 秒开锁窗口机制。

#### 6.9.3 窗口行为规则

| 事件 | 行为 |
| :--- | :--- |
| 用户按有权限的锁按钮 | 开锁，记录日志 |
| 用户按无权限的锁按钮 | 拒绝，提示无权限 |
| 10 秒窗口超时 | 退出验证状态，锁灯灭 |
| 按取消键 | 立即退出验证状态 |
| 窗口内再次按指纹 | 重新计时 10 秒 |

> 10 秒窗口内可多次开锁，避免每次开锁都需重新按指纹，提升实训场景体验。

## 7. 硬件设计

### 7.1 硬件连接图

```
ESP32-WROOM-32
├── UART2 (TX: GPIO17, RX: GPIO16)
│   └── AS608指纹模块
│       ├── VCC: 3.3V
│       ├── GND: GND
│       ├── TX: GPIO16 (ESP32 RX)
│       └── RX: GPIO17 (ESP32 TX)
│
├── GPIO输出 (继电器控制)
│   ├── GPIO23 → 继电器1 (Lock 0)
│   ├── GPIO22 → 继电器2 (Lock 1)
│   ├── GPIO21 → 继电器3 (Lock 2)
│   └── GPIO19 → 继电器4 (Lock 3)
│
├── GPIO输入 (按键)
│   ├── GPIO5  → 按键1 (Lock 0)
│   ├── GPIO18 → 按键2 (Lock 1)
│   ├── GPIO25 → 按键3 (Lock 2)
│   └── GPIO26 → 按键4 (Lock 3)
│
└── 电源
    ├── VIN: 5V
    └── GND: 接地
```

### 7.2 硬件选型清单

| 序号 | 组件名称 | 型号 | 数量 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | ESP32主控板 | ESP32-WROOM-32 | 1 | 核心控制模块 |
| 2 | 指纹识别模块 | AS608 | 1 | UART接口 |
| 3 | 继电器模块 | 4路继电器 | 1 | 控制门锁 |
| 4 | 按键 | 轻触按键 | 4 | 手动触发 |
| 5 | 电源模块 | 5V/2A | 1 | 供电 |
| 6 | 连接线 | 杜邦线 | 若干 | 连接各模块 |

### 7.3 门锁控制原理

- 继电器采用低电平触发或高电平触发（根据模块型号调整）
- 开锁时，GPIO输出有效电平，继电器吸合，门锁打开
- 延时3-5秒后，GPIO输出无效电平，继电器断开，门锁关闭
- 每个按键对应一个锁，按下按键触发指纹验证，验证通过后开锁

## 8. 安全考虑

### 8.1 数据安全

- 指纹模板在传输过程中进行加密
- 权限数据存储时进行校验和验证
- 通信数据采用校验和防止篡改

### 8.2 访问控制

- 系统管理员密码采用加密存储（SHA256）
- 上位机登录需要身份验证
- 权限变更需要管理员或老师授权

### 8.3 物理安全

- 指纹模块具有防拆卸保护
- 继电器输出增加保险丝保护
- 电源模块具有过流保护

### 8.4 Mesh 网络安全

- **Mesh密码保护**：ESP-MESH 启用 AES 加密，配置 Mesh 网络 password，未授权节点无法加入网络
- **白名单机制**：根节点维护允许加入的 MAC 白名单，拒绝陌生设备
- **USB直连隔离**：根节点 ↔ 上位机走USB物理串口，不暴露在无线网络中，无法被远程入侵
- **无外网暴露**：Mesh网络是封闭内网，不与互联网相连，避免远程攻击面
- **节点身份校验**：每个节点注册时上报 device_id + mesh_mac，上位机可双重校验
- **调试模式隔离**：AP+TCP 调试模式仅在维护时启用，日常关闭，避免开放无线热点

### 8.5 通讯链路可靠性

- Mesh层自动重传与重路由，单节点故障不影响整体通讯
- USB串口通讯稳定，无WiFi干扰风险
- 根节点心跳检测：上位机定期向Root发送HEARTBEAT，超时判定通讯中断
- 子节点离线缓存：Mesh断连时本地保存日志（最多100条），恢复后批量补传

```
     │── 分配权限 ───────►│            │            │
     │  (用户, 锁列表)    │            │            │
     │                    │── Serial.write ─►│            │
     │                    │  (SYNC_PERMISSIONS)│         │
     │                    │           │── esp_mesh_send ─►│
     │                    │           │            │
     │                    │           │            ▼
     │                    │           │       保存权限到Flash
     │                    │           │            │
     │                    │           │◄── esp_mesh_recv ─│
     │                    │           │  (CONFIG_SAVED)│
     │                    │◄── Serial.write ─│            │
     │◄── 同步完成 ───────│           │            │
```

### 9.3 开锁流程（Mesh链路）

```
用户      子节点(Mesh)   Root(USB)    上位机
  │            │             │            │
  │── 按下按键 ─►│             │            │
  │            │             │            │
  │── 指纹识别 ─►│             │            │
  │            │             │            │
  │            │── esp_mesh_send ─►│            │
  │            │  (FINGER_VERIFY)│           │
  │            │             │── Serial.write ─►│
  │            │             │            │
  │            │             │            ▼
  │            │             │       查询用户权限
  │            │             │            │
  │            │             │◄── Serial.write ─│
  │            │             │  (AUTH_OK)  │
  │            │◄── esp_mesh_recv ─│            │
  │            │  (permissions)│            │
  │            │             │            │
  │            ▼             │            │
  │       根据权限控制锁     │            │
  │            │             │            │
  │            │── esp_mesh_send ─►│            │
  │            │  (LOG_REPORT)│           │
  │            │             │── Serial.write ─►│
  │            │             │       (记录日志)
  │            │             │            │
  │◄── 开锁成功 ─│             │            │
```

#### 12.1.2 复杂度评估说明

- **难点1(模块2 Mesh)**：ESP-MESH 的 Root 选举、节点路由维护、节点掉线重路由需要深入理解 esp_mesh API；40节点规模首次部署可能遇到 Mesh 不稳定问题，需要调试

- **难点3(模块12 离线自治)**：断网时本地权限验证、断网期间日志缓存、恢复后批量同步需考虑多种异常情况

### 12.3 开发阶段划分与建议顺序

```
阶段1: POC验证(2台ESP32+1台上位机)
   ├─ ESP32: 1Root+1Node 跑通Mesh组网
   ├─ Root: USB CDC桥接跑通
   ├─ 上位机: SerialTransport + 协议帧 + REGISTER 跑通
   └─ 验证目标: 1台子节点通过Root转发开锁成功
        │
        ▼
阶段2: 核心功能闭环(3台ESP32)
   ├─ 协议: 实现REGISTER/FINGER_VERIFY/AUTH_OK/SYNC_PERMISSIONS
   ├─ ESP32: 指纹模块驱动+本地权限缓存+断网自治
   ├─ 上位机: 用户管理+权限配置+MeshBridge+SQLite
   └─ 验证目标: 断网期间仍可按指纹开锁,联网后日志补传
        │
        ▼
阶段3: 扩展到40节点
   ├─ 40台ESP32组网压力测试
   ├─ Root节点Mesh路由性能验证
   ├─ 批量权限同步性能验证
   └─ 验证目标: 40台同时在线,无丢消息
        │
        ▼
阶段4: 完善与优化
   ├─ OTA升级、配置界面、日志查看
   ├─ WiFi AP/STA链路实现

   └─ 验证目标: 满足正式部署要求
```

### 12.4 风险点与应对

| 风险点 | 概率 | 影响 | 应对措施 |
| :--- | :--- | :--- | :--- |
| 40节点Mesh不稳定 | 中 | 高 | 阶段1先用2节点验证,阶段3压力测试分批扩展(10/20/40) |
| Flash写入断电损坏 | 中 | 中 | A/B双区+魔数+CRC,启动时自动恢复 |
| AS608指纹模块兼容性 | 低 | 中 | 提前购买2-3个不同批次模块做兼容测试 |
| Mesh根节点单点故障 | 中 | 高 | Root掉线时,Mesh自动选举新Root(esp_mesh原生支持) |
| 上位机USB驱动兼容性 | 中 | 中 | 优先用CH340/CP2102方案,避免杂牌USB转串口 |
| 协议演进兼容 | 高 | 中 | 帧格式保留版本字段,OTA支持远程升级固件 |
| 权限数据上下行不一致 | 中 | 高 | 版本号机制+定期全量同步+用户主动触发同步 |
