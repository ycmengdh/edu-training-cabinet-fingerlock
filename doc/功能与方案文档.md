# ESP32指纹锁实训柜权限管理系统 - 功能与方案文档

> **现行架构摘要（2026-07-28）**  
> - 主控统一为 **ESP32-S3 N16R8**（16MB Flash + 8MB PSRAM）  
> - 多柜日常：**ESP-MESH** 自组网 → 根节点 → 上位机（USB 串口为主）  
> - 单柜维护：柜机 **UART0 直连** 上位机（与根节点上行同协议），**不是** AP+TCP  
> - 与早期「柜机 WiFi/TCP 直连上位机」草案冲突时，以 [`系统架构与组网说明.md`](系统架构与组网说明.md) 为准。

## 1. 项目概述

### 1.1 项目背景

本项目是针对学校实训场景设计的实训柜指纹权限管理系统。每个实训柜配备 **ESP32-S3 N16R8** 与指纹模块组成的指纹锁；多柜通过 **ESP-MESH** 自组网，由根节点汇聚后与上位机通信，实现指纹权限的远程管理和分配。单台柜机仍可通过 **UART0** 直连上位机做独立调试与控制。

### 1.2 项目目标

- 实现基于指纹识别的实训柜门锁控制
- 建立三级权限管理体系（系统管理员/老师/学生）
- 支持远程权限分配和管理
- 确保系统安全性和可靠性
- 多柜 Mesh 集中管理与单柜 UART 维护通道并存

### 1.3 应用场景

学校实训室中，每个实训柜配备一套指纹锁系统，学生和老师通过指纹识别打开对应的柜门，系统管理员负责整体权限管理。教室部署走 Mesh；产测或修柜时用单柜 UART。

### 2.4 V2.7 柜机本地交互流程（窗口化验证）

V2.7 对柜机本地开锁流程进行了反转，符合需求文档"先验证指纹 -> 10 秒操作窗口 -> 按键开锁"的设计：

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────────┐
│ STATE_WAIT_ │     │ STATE_VERIFIED_  │     │ 开锁（3s 自动   │
│ FINGER      │────▶│ WINDOW (10s)     │────▶│ 回锁）          │
│ 常态轮询    │ 验证│ 绿灯常亮         │ 按键│                 │
│ 绿灯慢闪    │ 成功│ 等待按键         │     │                 │
└─────┬───────┘     └────────┬─────────┘     └─────────────────┘
      │                      │ 超时/取消
      │ 识别失败              ▼
      │ 红灯闪3次        ┌────────────┐
      └─────────────────▶│ 回到 WAIT_ │
                         │ FINGER     │
                         └────────────┘
```

**状态机**：
- `STATE_WAIT_FINGER`：开机即进入，常态轮询 AS608。识别中绿灯慢闪（500ms 周期）。
- `STATE_VERIFIED_WINDOW`：指纹匹配成功且本地权限缓存命中后进入，绿灯常亮。10 秒内按下有权限的锁按键即开锁（继电器 3s 后自动回锁）；超时或按取消键 K5 则清空验证权限回 `STATE_WAIT_FINGER`。
- `STATE_ENROLLING`：主/副指纹录入，期间不轮询识别。

**指纹状态 LED**（绿 GPIO41 / 红 GPIO38）：
- 识别中：绿灯慢闪
- 成功：绿灯常亮（持续至窗口结束）
- 失败：红灯闪烁 3 次（约 1.5s）后熄灭
- 窗口超时/取消/开锁完成：全部熄灭

**取消键 K5**：在验证窗口期内按下立即终止本次验证流程并灭灯；在录入期间按下中止录入。长按 10s 仍用于切换 Mesh/Debug 模式。

### 2.5 V2.7 设备专属副指纹

**痛点**：同一用户在多台柜子有权限时，部分设备因指纹采集角度/磨损等原因识别不灵敏，需在对应柜子重录适配指纹，但不希望影响其他设备的主指纹。

**方案**：
- **主指纹**：学生/老师统一标准指纹，存储在上位机 SD 卡，用于批量分配设备权限，全设备通用识别。AS608 物理槽位 = 全局 `fingerprint_id`。
- **设备专属副指纹**：单台柜子本地录入，仅在当前柜子生效。AS608 物理槽位由柜子 `Storage::allocLocalFpId()` 随机分配，柜子 NVS 自维护"AS608 槽位 ↔ 用户 ↔ 权限"映射表（`is_backup=true` 标记）。
- **录入后二选一**：
  1. 覆盖全局主指纹：调用 `UserService.AssignFingerprint` 更新 SD 卡 `users` 表的 `fingerprint_id`，并 `SyncAllPermissions` 全局下发。
  2. 仅作为本机备用指纹：不修改 `users` 表，仅保留柜子本地映射。
- **不被全局同步覆盖**：`replaceAllPermissions` 在权限全量同步时保留 `is_backup=true` 的记录，仅替换主指纹记录。
- **验证流程适配**：`STATE_WAIT_FINGER` 中 `verifyFingerprint()` 返回 AS608 物理槽位 ID，`Storage::findPermissionByAs608Id()` 按物理槽位查找权限记录（主/副共用同一权限表）。

### 2.6 V2.7 三层角色数据范围隔离

| 角色 | 可见范围 | 可操作范围 |
| :--- | :--- | :--- |
| 系统管理员 | 全部数据 | 全部增删改查 |
| 教师 | 本班学生 + 自己 + 管理员（只读） | 仅本班学生（增删改权限/指纹/密码） |
| 学生 | 仅自己 | 仅查看自己的日志 |

**实现**：`IDataScopeContext` 接口 + `DataScopeContext` 默认实现，从 `App.CurrentUser` 读取当前角色。
- `UserService.GetVisibleUsers()` / `GetVisibleUsersBrief()` / `GetVisibleUsersByRole()` 提供范围过滤的查询。
- `UserService` / `PermissionService` 写操作调用 `Scope.EnsureCanModify(target)`，教师尝试操作非本班用户时抛 `UnauthorizedAccessException`。
- `LogService.QueryVisibleLogs()` / `CountVisibleLogs()` / `AggregateVisibleFailReasons()` 按可见用户 ID 集合过滤日志。
- UI 层（`UserManagePage` / `PermissionPage` / `LogPage`）改用 Visible 变体；`MainWindow.ApplyRoleVisibility` 教师显示用户管理/权限/设备/指纹模板/日志页。

## 4. 系统架构设计

### 4.0 ESP-MESH 自组网方案

#### 4.0.1 组网问题分析

当系统部署40个柜子（40台ESP32设备）时，传统WiFi路由器方案面临以下痛点：
- 需要部署企业级路由器/AP，且要求其能稳定承载40+客户端并发
- 每台ESP32都需要预先配置 WiFi SSID/密码、上位机IP/端口
- 路由器成为单点故障：路由器宕机整个系统瘫痪
- 实训柜金属外壳对WiFi信号衰减严重，单个AP覆盖可能不足
- 一旦换场地或换路由器，40台设备全部需要重新配网

#### 4.0.2 组网方案对比

| 方案 | 描述 | 优点 | 缺点 | 推荐度 |
| :--- | :--- | :--- | :--- | :--- |
| **方案A：路由器组网** | 部署路由器，所有ESP32作为客户端连接 | 实时通信、协议成熟 | 需路由器基础设施、配网繁琐、单点故障 | ★★★☆☆ |
| **方案B：ESP32开热点** | ESP32开AP热点，上位机逐个连接 | 无需路由器 | 不可扩展、无法实时管理40台 | ★☆☆☆☆ |
| **方案C：ESP-MESH自组网** | 40台ESP32自动组树状Mesh，根节点USB串口接上位机 | **零路由器、零配网、自动修复、单点接入** | 单跳延迟略增（可接受） | **★★★★★** |

#### 4.0.3 推荐方案：ESP-MESH 自组网 + USB串口桥接

**核心思想**：40台ESP32通过乐鑫官方 ESP-MESH 协议自动组成树状网络，其中**1台作为根节点（Root）**通过USB串口直连上位机。所有设备间通信走Mesh，根节点负责 Mesh ↔ 串口 双向转发。

```

│                      实训室 ESP-MESH 网络拓扑                       │
│                                                                      │
│    ┌─────────┐    USB串口     ┌──────────────┐                      │
│    │ 上位机  │◄──────────────►│  根节点      │  ESP32 #1 (Root)    │
│    │  PC     │   921600 bps   │  ESP32       │                      │
│    │ C# WPF  │                └──────┬───────┘                      │
│    └─────────┘                       │                              │
│                                      │                              │
│                          ESP-MESH 自组网（自动路由）                │
│                                      │                              │
│            ┌─────────────────────────┼─────────────────────────┐   │
│            │                         │                         │   │
│       ┌────▼─────┐              ┌────▼─────┐              ┌────▼───▼┐│
│       │ ESP32 #2 │     ...      │ ESP32 #20│     ...      │ESP32#40││
│       │ 实训柜1  │              │ 实训柜19 │              │实训柜39││

│            │                                                        │

│                                                                      │
│   关键特性：                                                        │
│   - 无需路由器、无需配WiFi密码                                       │
│   - 上电自动组网，自动选举根节点                                     │
│   - 节点故障自动重路由，单点失效不影响整体                           │
│   - 根节点USB直连PC，零网络配置                                      │
│   - 所有设备与上位机之间通过根节点透明转发                           │
```

#### 4.0.4 ESP-MESH 协议说明

**ESP-MESH** 是乐鑫官方为ESP32推出的WiFi Mesh协议（组件名 `esp_mesh`），特点：

| 特性 | 说明 |
| :--- | :--- |
| 拓扑结构 | 树状（也支持链状），自动维护父子关系 |
| 节点容量 | 官方标称支持数十至数百节点，40台设备完全在能力范围内 |
| 自组网 | 上电自动扫描、自动选举根节点、自动加入网络 |
| 自修复 | 任一节点掉线，子节点自动重新寻找父节点接入 |
| 通信方式 | 节点间通过Mesh层收发数据包，无需TCP连接 |
| 传输层 | 应用层 B1/0F 信封走 Mesh 数据包（可无外层 A5）；复杂 payload 内可含 JSON |
| 安全性 | 支持 Mesh 密码（AES），防止未授权节点加入 |
| 本项目硬件 | **ESP32-S3 N16R8**（根节点与柜机统一） |

**树状拓扑示意（40节点典型结构）**：

```
                    [Root] ESP32#1 ◄─── USB串口 ───► 上位机
                   /      |      \
                  /       |       \
            [Node#2]  [Node#3]  [Node#4]
            /   \       |        /   \
       [Node#5][#6]  [Node#7][#8][#9]
          ...           ...        ...
        叶子层：约30+个节点
```

- 根节点：1台，固定为ESP32#1（可通过配置或自动选举）
- 中间节点：约6-10台，承担数据转发
- 叶子节点：约30台，只收发自己业务数据
- 推荐拓扑深度：3-4层（避免过深增加延迟）

#### 4.0.5 节点角色定义

| 节点角色 | 数量 | 硬件 | 职责 | 与上位机通讯 |
| :--- | :--- | :--- | :--- | :--- |
| **根节点 (Root)** | 1台 | ESP32 + USB线 | Mesh根 + 串口桥接 | USB串口直连 |
| **普通节点 (Node)** | 39台 | ESP32 | 指纹锁控制 + Mesh通讯 | 经Mesh路由到Root |

**根节点特殊处理**：
1. Mesh 启动时固定为 Root（本工程根节点固件角色固定，不与柜机混刷）
2. 主机口为 **USB-Serial-JTAG / CDC**（GPIO19/20），921600，与 PC 通讯
3. 在 Mesh 与上行串口之间双向转发应用层消息（现行：**A5/5A 帧 + B1/0F 二进制信封**；复杂 payload 内可含 JSON）
4. 根节点同时作为 **SD 业务数据中心**（用户/权限/模板等 JSON 表），一般不兼作柜机指纹锁

**普通节点（柜机）行为**：
1. Mesh 启动为 Node，自动寻找父节点 / Root
2. 日志与状态通过 Mesh 发往 Root；开锁鉴权在**本机**完成
3. 监听 Mesh 接收，处理上位机经 Root 下发的命令
4. 应用层消息与上位机 `Message` / `cmd_id` 对齐；线上主路径为二进制信封，而非整包裸 JSON

#### 4.0.6 节点身份与设备编号映射

每个ESP32在Mesh网络中拥有两类身份：

| 身份类型 | 标识 | 用途 | 获取方式 |
| :--- | :--- | :--- | :--- |
| **Mesh Layer Address** | 6字节MAC | Mesh内部路由 | 启动时自动获取 |
| **Device ID** | 字符串（如 `CABINET_001`） | 业务层标识 | Flash预存 |

**上位机识别设备流程**：
1. ESP32上电组网成功后，向Root发送 `REGISTER` 消息（含 `device_id` 和 `device_name`）
2. Root转发到串口给上位机
3. 上位机记录 `device_id` ↔ Mesh MAC 映射
4. 后续命令通过 `device_id` 路由（Root内部维护 `device_id` → Mesh MAC 表）

#### 4.0.7 USB 串口桥接设计（根节点 ↔ 上位机）

**串口参数（现行）**：

| 项目 | 值 | 说明 |
| :--- | :--- | :--- |
| 物理接口 | 根节点板载 USB | ESP32-S3 USB-Serial-JTAG |
| 虚拟串口 | CDC（`ARDUINO_USB_CDC_ON_BOOT=1`） | 上位机看到普通 COM 口 |
| 波特率 | `921600` bps | 与柜机 UART0 调试口一致 |
| 数据位 | 8 / 无校验 / 停止位 1 | 标准配置 |
| 流控 | 无 | 简化接线 |
| 外层帧 | `0xA5 0x5A` + 长度 + payload + CRC16/MODBUS | 见 `ProtocolFrame` / `FrameCodec` |
| 应用层 | `0xB1 0x0F` 二进制信封 | 简单命令定长；复杂 data 仍为 JSON 字节 |

实现落在 `root_node/src/mesh_bridge.*` 与 `common/serial_uplink.*`：Mesh 收包转上行、串口收包按 `device_id` 路由到柜机。示意级伪代码已过时，以源码为准。

#### 4.0.8 双模式保留（Mesh 模式 + 单柜 UART 模式）

为兼顾多柜部署与单台维护，**柜机**保留两种工作模式（长按任意键约 10s 切换，重启生效）：

| 模式 | 固件名 | 触发 | 用途 | 通讯方式 |
| :--- | :--- | :--- | :--- | :--- |
| **Mesh 模式** | `MODE_MESH`（默认） | 上电默认 | 多柜集中部署 | ESP-MESH → Root → 上位机；柜机 UART0 协议口也可旁路开启 |
| **单柜 UART** | `MODE_DEBUG` | 长按键 ~10s | 单台开发 / 无 Mesh 检修 | **仅 UART0（GPIO43/44，921600）** 直连上位机，协议与 Root 上行相同 |

**模式切换**：
- 长按任意键保持约 10 秒 → 切换 Mesh ↔ Debug 并重启
- 板载状态 LED：Mesh 已连接慢闪 / 连接中中速闪（细节见柜机固件）

> **重要**：单柜模式是 **UART 串口协议直连**，**不是** 历史草案中的「AP 热点 + TCP」。  
> 上位机打开该柜 COM 口后，用与接根节点相同的帧协议，对**该柜 `device_id`** 下发命令即可独立控制。  
> 硬件接线见 `esp32_firmware/doc/柜子/IO分配.md`；脚本见 `debug/README.md`（`--links uart`）。

#### 4.0.9 上位机 Mesh 桥接设计

上位机通过 `Network/MeshBridge` + `ITransport` 接入：

| 传输 | 典型用途 |
| :--- | :--- |
| `SerialTransport` | 接根节点 USB（多柜主路径）；或接单柜 UART0（单台维护） |
| `TcpClientTransport` / `TcpServerTransport` | 根节点 AP/STA 上行可选 |

业务层使用统一 `Message` / `cmd_id`；发送走 `BinaryMessageCodec` 装入 A5/5A 帧。  
详细协议见 `doc/协议统一说明.md`。

#### 4.0.10 离线缓存与断网容错

虽然Mesh根节点USB直连PC可靠性高，仍保留离线容错能力：

| 故障场景 | 系统行为 |
| :--- | :--- |
| 某子节点掉线 | Mesh自动重路由，该节点业务中断但其他节点正常 |
| 根节点USB断开 | 上位机立即检测到，所有设备离线缓存日志，根节点恢复后批量同步 |
| 单节点与Mesh失联 | 本地缓存开锁日志（最多100条），网络恢复后批量上报 |
| 上位机软件关闭 | ESP32继续工作（权限已缓存），日志本地保存，PC重启后同步 |

#### 4.0.11 部署使用流程

**首次部署**：
1. 烧录固件到40台ESP32（统一固件，通过Flash配置区分Root/Node）
2. 设置1台为Root节点（写入 `is_root=true` 配置）
3. Root节点通过USB连接PC
4. 上电后40台ESP32自动组网（约30-60秒）
5. 上位机打开串口，自动识别40台设备注册消息

**日常使用**：
1. 上位机启动 → 自动连接Root串口
2. 40台ESP32上电 → 自动加入Mesh网络
3. 用户按指纹 → 设备Mesh发往Root → Root串口转PC → PC验证后回传
4. 日志实时上传，权限变更实时下发

**新增/更换设备**：
1. 烧录相同固件，配置 `device_id`
2. 上电即可自动加入Mesh网络（无需任何配网操作）

**场地迁移**：
- 整体打包40台ESP32 + 1根USB线 + 1台PC
- 无需重新配网，上电自动组网

#### 4.0.12 硬件部署建议

**Root节点位置**：
- 放置在实训室中央位置，确保Mesh无线覆盖良好
- 通过USB延长线连接到上位机PC
- 单独供电（USB供电或独立5V电源）

**子节点布局**：
- 每台ESP32安装在实训柜内部，外接天线引出柜体（如信号衰减严重）
- 避免金属柜体完全封闭ESP32天线
- 相邻实训柜间距建议 < 10米（Mesh单跳可靠距离）

**Mesh网络优化**：
- 拓扑深度建议 ≤ 4 层
- 中间层节点选择信号好的位置（自动选举优先信号强度）
- 必要时增加1-2台纯转发节点（不接指纹锁，仅作Mesh中继）

#### 4.2.3 ESP32 Flash 存储设计

本项目主控为 **ESP32-S3 N16R8（16MB Flash + 8MB PSRAM）**。分区表见 `esp32_firmware/common/partitions_16MB_log.csv`；权限与配置在 **NVS**，离线日志在自定义 **logstore** 分区（`LOG_STORE_OFFSET`，见 `config_common.h`）。不做 OTA 双分区（用户确认串口烧录即可）。

##### 存储技术选型（现行）

| 数据类型 | 存储方式 | 理由 |
| :--- | :--- | :--- |
| 设备配置 | **NVS** | 磨损均衡 + 键值 API；Mesh 密码等可写 NVS |
| 柜机权限缓存 | **NVS Blob（A/B + CRC）** | 量小、低频写；全量同步可保留副指纹记录 |
| 离线开锁日志 | **Flash 环形 logstore** | 频繁写，自定义磨损；Mesh 恢复后补传 |
| 指纹模板（柜机） | **AS608 内部 Flash** | 物理槽位；全局主指纹 / 本机副指纹分策略 |
| 业务权威数据 | **根节点 SD 卡 JSON 表** | users/permissions/templates 等，非柜机 Flash |
| 设备列表(Root用) | **NVS Blob** | 量小,低频写 |

##### 权限数据存储格式（紧凑二进制）

为节省 Flash 空间，权限数据采用紧凑二进制而非 JSON 存储：

```
权限数据文件结构（perm_store 分区内,通过NVS Blob存取）：
┌────────────────┬─────────────────────────────────────┐
│ 文件头 (16B)   │ 权限版本(4B) + 用户数(2B) +          │
│                │ 保留(2B) + CRC32(4B) + 魔数(4B)     │
├────────────────┼─────────────────────────────────────┤
│ 用户记录数组   │ 每条记录 12B,见下表                  │
└────────────────┴─────────────────────────────────────┘

单条用户记录(12B):
┌──────────────┬──────────┬──────────┬───────────┬──────────────┐
│ fingerprint_id│ user_id  │ lock_perm│ role      │ expire_days  │
│ 2B           │ 4B       │ 1B(bit0-3)│ 1B       │ 4B(距2000-01-01天数)│
└──────────────┴──────────┴──────────┴───────────┴──────────────┘
```

| 字段 | 长度 | 说明 |
| :--- | :--- | :--- |
| fingerprint_id | 2B | AS608指纹ID(1-30000) |
| user_id | 4B | 上位机用户ID(数字形式,够用) |
| lock_perm | 1B | 4个锁权限,bit0-3分别对应Lock0-3 |
| role | 1B | 0=admin 1=teacher 2=student |
| expire_days | 4B | 过期天数(距2000-01-01),0xFFFFFFFF表示永久 |

##### 容量评估

| 项目 | 单条大小 | 数量上限 | 总占用 |
| :--- | :--- | :--- | :--- |
| 用户权限记录 | 12B | 200用户 | 2.4KB |
| 文件头 | 16B | - | 16B |
| **权限数据总计** | - | - | **≈2.5KB**(远小于128KB分区) |

> 即使扩展到 1000 用户，权限数据仅 12KB，Flash 完全够用。权限分区预留 128KB 是为了写入磨损均衡（NVS内部使用）。

##### 离线日志存储（环形缓冲）

权限数据通过 NVS 存储，但离线日志写入频繁（每次开锁一条），不适合 NVS 的"擦-写"模式，自定义环形缓冲：

```
log_store分区(128KB = 32个4KB扇区):
┌──────┬──────┬──────┬──────┬─────┬──────┐
│扇区0 │扇区1 │扇区2 │扇区3 │ ... │扇区31│
└──────┴──────┴──────┴──────┴─────┴──────┘
   │      │      │      │             │
   │      │      │      │             └─写指针当前指向
   │      │      │      └─已写满
   │      │      └─已写满
   │      └─已写满
   └─起始
```

**单条日志记录(32B)**：
```
┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────────┐
│ log_seq  │ user_id  │ fp_id    │ lock_id  │ result   │ timestamp    │
│ 4B       │ 4B       │ 2B       │ 1B       │ 1B       │ 4B(unix时间) │
└──────────┴──────────┴──────────┴──────────┴──────────┴──────────────┘
+ 16B预留(可扩展存reason等)
```

- 单扇区(4KB)可存 128 条日志
- 总容量 32×128 = **4096 条日志**
- 按每天100条估算，可缓存约 40 天
- 写满后自动覆盖最旧扇区（环形）

**磨损均衡**：写入按扇区顺序轮转，写满一扇区才擦下一扇区。每扇区寿命10万次，32扇区可承受 320万次擦写，按每天100条日志估算可使用 **800+年**。

##### 数据完整性保障

| 风险 | 措施 |
| :--- | :--- |
| 写入中途断电 | 双区写入(A/B两份),写完一份再擦另一份,任一份CRC通过即用 |
| Flash位翻转 | 每份末尾存CRC32,启动时校验,失败回退另一份 |
| 跨分区误写 | 分区头加魔数(0xA5A55A5A),校验魔数才认为有效 |
| NVS损坏 | NVS自带磨损均衡+加密校验,损坏时整体重置并请求上位机全量同步 |
| 权限数据丢失 | 启动时CRC失败→向Root上报PERM_LOST→上位机自动全量同步 |

##### 启动加载流程

```
ESP32上电
   │
   ▼
读取perm_store的A区 ──► CRC校验
   │                      │
   │                   ┌──┴──┐
   │                   │通过 │失败
   │                   ▼     ▼
   │              使用A区  读B区CRC校验
   │                   │     │
   │                   │  ┌──┴──┐
   │                   │  │通过 │失败
   │                   │  ▼     ▼
   │                   │ 使用B区 权限为空
   │                   │        │
   └───────────────────┴────────┴──► 加入Mesh
                                       │
                                       ▼
                            上报REGISTER + 当前权限版本号
                                       │
                                       ▼
                            上位机比对版本号,不一致则SYNC_PERMISSIONS全量同步
```

## 5. 通信协议设计

### 5.1 通信方式

现行方案为 **ESP-MESH 多柜主路径 + 单柜 UART 辅路径**，根节点再以上行串口（或可选 TCP）接上位机：

| 链路段 | 协议 | 介质 | 说明 |
| :--- | :--- | :--- | :--- |
| **柜机 ↔ 根节点** | ESP-MESH | Wi‑Fi 2.4G | 多柜自组网；应用层 B1/0F 信封（可无外层 A5） |
| **根节点 ↔ 上位机** | A5/5A 帧 + B1/0F | USB CDC 串口（主）/ AP·STA TCP（可选） | 921600；复杂 payload 内可含 JSON |
| **单柜 ↔ 上位机** | 同上（与 Root 上行同协议） | 柜机 UART0 + USB-TTL | Debug 模式，不经 Mesh |

**关键特性**：
- 线上主路径已统一为 **二进制信封**；整包裸 JSON 仅作旧固件兼容，新发送侧应避免
- 业务层以 `cmd_id` / `device_id` 路由，不感知底层是 Mesh 还是 UART
- 单台维护通道是 **UART**，不是 AP+TCP  
- 细节见 `doc/协议统一说明.md`、`doc/系统架构与组网说明.md`

### 5.2 数据格式

应用层逻辑字段（概念模型；线上由 B1/0F 二进制头承载 cmd/device，复杂 data 可为 JSON）：

| 字段 | 类型 | 说明 |
| :--- | :--- | :--- |
| `cmd` / `cmd_id` | 名称或数值 | 命令类型（`CmdIds` / `cmd_ids.h`） |
| `device_id` | string | 设备唯一标识（业务层路由依据） |
| `data` / payload | object 或二进制 | 数据内容 |
| `timestamp` | 数值/字符串 | 时间戳 |
| 可选 HMAC | 签名块 | 敏感命令，部署期可开启 |

**消息封装链路（主路径示意）**：

```
[业务层]  Message / cmd_id + payload
   │
   ▼
[柜机] B1/0F 应用信封 ──Mesh──► [Root] ──装 A5/5A 帧──► 上位机 USB/TCP
   │
   └─ 单柜 Debug：柜机直接经 UART0 发 A5/5A+信封 ──► 上位机 USB-TTL

[上位机] FrameCodec 拆帧 → BinaryMessageCodec 解信封 → MessageHandler
```

### 5.5 消息帧格式设计

为保证 Mesh 数据包与 USB 串口传输的可靠性，定义统一的二进制帧格式。JSON 文本作为 payload 封装在帧内。

#### 5.5.1 帧结构

```
┌──────────┬──────────┬──────────┬─────────────────────┬──────────┐
│ 帧头     │ 版本     │ 负载长度 │  Payload (JSON)     │ CRC16    │
│ 0xA5 0x5A│ 1 byte   │ 2 byte   │  N byte (≤1400)     │ 2 byte   │
└──────────┴──────────┴──────────┴─────────────────────┴──────────┘
   2B         1B         2B           N B                  2B
```

| 字段 | 长度 | 说明 |
| :--- | :--- | :--- |
| 帧头 | 2B | 固定 `0xA5 0x5A`，用于接收端同步 |
| 版本 | 1B | 协议版本号，当前 `0x01`，便于未来升级 |
| 负载长度 | 2B | Payload 字节数（大端序），最大 1400B（ESP-MESH 单包上限） |
| Payload | N B | JSON 文本（UTF-8编码，**不含**末尾 `\n`） |
| CRC16 | 2B | 对"版本+长度+Payload"做 CRC-16/MODBUS 校验 |

> **说明**：原 V1.0 的"JSON + \n"分隔符方案在 USB 串口下仍可保留作为调试用，正式通信使用本帧格式。两种方案通过版本号区分。

#### 5.5.2 CRC16 校验

- 算法：CRC-16/MODBUS（多项式 0xA001）
- 计算范围：版本字段 + 长度字段 + Payload（不含帧头和 CRC 字段本身）
- 接收端校验失败：丢弃该帧，统计 `crc_error_count`，不上报应用层

```c
// ESP32 端 CRC16 计算（MODBUS多项式）
uint16_t crc16(const uint8_t *data, size_t len) {
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < len; i++) {
        crc ^= data[i];
        for (int j = 0; j < 8; j++) {
            crc = (crc & 1) ? (crc >> 1) ^ 0xA001 : (crc >> 1);
        }
    }
    return crc;
}
```

#### 5.5.3 帧大小与 MTU 适配

| 链路 | MTU | 单帧最大 Payload | 超长消息处理 |
| :--- | :--- | :--- | :--- |
| ESP-MESH (P2P) | 1500B | **1400B** | 自动分片（见 5.5.4） |
| USB CDC 串口 | 无限制 | 不限 | 不分片，直接发 |
| TCP (WiFi链路) | 1500B | 1400B | 自动分片 |

#### 5.5.4 大消息分片机制

当 Payload > 1400B（如 `SYNC_PERMISSIONS` 一次同步40用户权限），启用分片：

```
分片头（4B，加在 Payload 前面）：
┌──────────┬──────────┬──────────┐
│ 消息ID   │ 分片序号 │ 总分片数 │
│ 1B       │ 1B       │ 1B       │
└──────────┴──────────┴──────────┘
（保留1字节用于未来扩展）
```

- 接收端按 `消息ID` 缓存分片，收齐后拼接、校验、上报应用层
- 超时未收齐（5秒）：丢弃已收分片，请求重发

### 5.7 交互时序与流控机制

#### 5.7.1 请求-响应超时

| 命令类型 | 超时时间 | 失败重试次数 | 说明 |
| :--- | :--- | :--- | :--- |
| FINGER_VERIFY → AUTH_OK/FAIL | 2秒 | 2次 | 影响用户体验,超时短 |
| CONTROL_LOCK → 确认 | 1秒 | 1次 | 锁动作需快速响应 |
| ADD_FINGERPRINT → 确认 | 10秒 | 0次 | 涉及指纹采集,不可重试 |
| SYNC_PERMISSIONS → 确认 | 30秒 | 2次 | 大数据量,允许较长 |
| READ_CONFIG → CONFIG_RESPONSE | 3秒 | 2次 | 常规查询 |
| WRITE_CONFIG → CONFIG_SAVED | 5秒 | 1次 | 涉及Flash写入 |
| LOG_REPORT → 确认(ACK) | 3秒 | 3次 | 日志不可丢,重试多 |
| HEARTBEAT → 无需响应 | - | - | 单向保活 |

#### 5.7.2 ACK 确认机制

对于不可丢失的下行命令（`SYNC_PERMISSIONS` / `ADD_FINGERPRINT` / `WRITE_CONFIG` / `CONTROL_LOCK`），下位机处理后需回 ACK：

```json
{
  "cmd": "ACK",
  "device_id": "CABINET_001",
  "data": {
    "original_cmd": "SYNC_PERMISSIONS",
    "original_msg_id": "M20260712001",
    "result": "success",      // success/fail
    "error_code": 0,
    "error_msg": ""
  }
}
```

> 每条命令携带 `msg_id`（上位机生成,格式 `M+yyyyMMdd+序号`），下位机 ACK 时原样回传。

#### 5.7.3 重传策略

```
发送命令(msg_id=X) ──► 等待ACK(超时T)
                          │
              ┌───────────┴───────────┐
              │ 收到ACK(X)            │ 超时未收到
              ▼                       ▼
           完成                  重试次数+1
                                ┌─────┴─────┐
                                │ < 最大次数 │ ≥ 最大次数
                                ▼           ▼
                            重发命令(X)   标记失败,上报错误
```

#### 5.7.4 心跳与连接保活

- **上位机 → Root**：每 30 秒发一次 `HEARTBEAT`，连续 3 次无响应判定链路断开
- **Root → 子节点**：Mesh层自带保活，应用层每 60 秒轮询一次状态（`READ_STATUS`）
- **子节点 → Root**：每 60 秒主动上报 `STATUS_REPORT`

#### 5.7.5 流控与拥塞避免

- **单设备消息限速**：下位机同一时刻只允许 1 条未确认命令在途，避免 Mesh 拥塞
- **批量操作错峰**：上位机批量同步权限时，每台设备间隔 200ms 发送，避免 Mesh 风暴
- **日志批量上报**：下位机本地缓存日志，每 10 秒批量上报一次（最多 20 条），而非逐条上报
- **断网重连退避**：Mesh 失联后重连采用指数退避（5s/10s/20s/40s/60s 封顶）

## 7. 硬件设计

> **柜机真实 IO 以** `esp32_firmware/doc/柜子/IO分配.md` **与** `cabinet_node/src/config.h` **为准**（下表为摘要，旧版 WROOM-32 直驱 GPIO 图已废弃）。

### 7.1 柜机连接摘要（ESP32-S3 N16R8）

```
ESP32-S3 N16R8（柜机）
├── UART0 (TX: GPIO43, RX: GPIO44) ── USB-TTL ── 上位机（单柜控制 / 旁路）
├── UART2 (TX: GPIO17, RX: GPIO18) ── AS608 指纹
├── GPIO42 / GPIO21 ── 指纹上电控制与状态
├── 74HC595 (DS=GPIO4, STCP=GPIO15, SHCP=GPIO16) ── 4 锁 + 锁 LED
├── 按键 K1~K5：GPIO47 / 48 / 45 / 39 / 40
├── 指纹状态 LED：绿 GPIO41 / 红 GPIO38
└── 板载状态 LED：GPIO2（Mesh 指示）
```

根节点另接 SD_MMC、0.96" TFT；主机口为 USB CDC，不占用柜机这套外设脚。

### 7.2 硬件选型清单

| 序号 | 组件名称 | 型号 | 数量 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | ESP32 主控 | **ESP32-S3 N16R8** | 每柜 1 + 根节点 1 | 16MB Flash + 8MB PSRAM |
| 2 | 指纹识别模块 | AS608 / 兼容 | 每柜 1 | UART |
| 3 | 锁驱动 | 4 路继电器 + 74HC595 | 每柜 1 套 | 见 IO 分配 |
| 4 | 按键 | 轻触按键 | 每柜 5 | 4 开锁 + 1 取消 |
| 5 | 根节点 SD / 屏 | SD 卡 + ST7735 等 | 根节点 1 套 | 业务数据与显示 |
| 6 | 单柜调试线 | USB-TTL | 按需 | 接柜机 UART0 |

### 7.3 门锁控制原理

- 锁通道经 74HC595 扩展，默认态与脉冲宽度由固件 `lock_control` 保证上电不误开
- 开锁后约 3s 自动回锁（以固件常量为准）
- **V2.7 流程**：先指纹验证 → 10s 窗口内有权限锁 LED 提示 → 再按对应键开锁（不是「先按键再验证」）

## 8. 安全考虑

### 8.1 数据安全

- 指纹模板在传输过程中进行加密
- 权限数据存储时进行校验和验证
- 通信数据采用校验和防止篡改

### 8.2 访问控制

- 系统管理员密码采用加密存储（SHA256）
- 上位机登录需要身份验证
- 权限变更需要管理员或老师授权

### 8.3 物理安全

- 指纹模块具有防拆卸保护
- 继电器输出增加保险丝保护
- 电源模块具有过流保护

### 8.4 Mesh 网络安全

- **Mesh密码保护**：ESP-MESH 启用 AES 加密，配置 Mesh 网络 password，未授权节点无法加入网络
- **白名单机制**：根节点维护允许加入的 MAC 白名单，拒绝陌生设备
- **USB直连隔离**：根节点 ↔ 上位机走USB物理串口，不暴露在无线网络中，无法被远程入侵
- **无外网暴露**：Mesh网络是封闭内网，不与互联网相连，避免远程攻击面
- **节点身份校验**：每个节点注册时上报 device_id + mesh_mac，上位机可双重校验
- **单柜 UART 隔离**：Debug 模式仅在维护时使用（UART 物理直连），日常部署保持 Mesh；不在柜机上长期开业务 AP 热点

### 8.5 通讯链路可靠性

- Mesh层自动重传与重路由，单节点故障不影响整体通讯
- USB串口通讯稳定，无WiFi干扰风险
- 根节点心跳检测：上位机定期向Root发送HEARTBEAT，超时判定通讯中断
- 子节点离线缓存：Mesh断连时本地保存日志（最多100条），恢复后批量补传
