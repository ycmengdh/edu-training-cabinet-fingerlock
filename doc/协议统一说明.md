# 协议统一说明（V2.8）

> 链路场景：多柜经 **Mesh → 根节点 USB**；单柜可经 **柜机 UART0** 直连。  
> **两路使用同一套外层帧 + 应用信封**，不是两套业务协议。硬件与组网见 `系统架构与组网说明.md`。

## 结论：不是两套业务协议，而是两层封装 + 一种遗留兼容

历史上容易误判为“两种协议”的原因，是线上同时出现了：

1. **外层链路帧** `0xA5 0x5A ... CRC16`（`ProtocolFrame` / `FrameCodec`）
2. **应用层二进制信封** `0xB1 0x0F ... cmd_id/msg_id/device_id/payload`（`app_protocol` / `BinaryMessageCodec`）
3. **遗留整包 JSON**（整帧 payload 直接是 `{"cmd":...}`，旧路径）

### 统一后的主路径（推荐/现行）

```
上位机/节点
  → 应用层 B1/0F 二进制信封
       - 简单命令 payload：定长二进制（CONTROL_LOCK / ACK / ERROR / HEARTBEAT）
       - 复杂命令 payload：UTF-8 JSON 对象字节（SD_* / SYNC_* / CONFIG / LOG 等）
  → 外层 A5/5A 链路帧（USB/TCP 上行）
  → Mesh 上可直接传应用信封（无 A5）
```

**不是“全部改成纯 JSON 包”**，也不是“全部改成无 JSON 的纯二进制业务字段”。

正确统一方式是：

- **路由/控制面**：二进制信封（cmd_id、msg_id、device_id、flags）
- **复杂业务 data**：仍用 JSON（便于 SD 表、配置、权限行扩展）
- **整包 JSON 消息**：仅兼容旧固件；新代码发送侧应拒绝裸 JSON

### 为什么保留 JSON payload？

- SD 表（users/classes/permissions…）本身是 JSON 文档存储
- 权限同步行、配置项字段经常演进，定长结构成本高
- ESP32 侧已有 ArduinoJson 处理路径；二进制信封避免了大包 JSON 外层二次解析与 `\0` 截断问题

### 本次代码对齐点

| 位置 | 变化 |
| --- | --- |
| 根节点 `cmdSdQuery` | 空表/缺表返回 `[]`，不再 `not found` 导致上位机整表失败 |
| 根节点 Mesh 应答 | HEARTBEAT_ACK / LOG_REPORT_ACK / TIME_SYNC 优先二进制信封 |
| `MeshBridge` 路由失败 | ERROR 优先二进制上行 |
| 上位机 `MeshBridge.SendJson` | 只接受可映射为 Message 的内容并转二进制；拒绝裸 JSON |
| `SdBusinessSyncService` | 空表成功、JSON 形态归一、失败重试、users 成功即可继续 |

### 开发约定

1. 新增命令：先在 `cmd_ids.h` / `CmdIds.cs` 登记 ID 与名字
2. 发送：上位机用 `Message.Create` → `MeshBridge.Send*`（内部 `BinaryMessageCodec`）
3. 固件发送：`MeshComm::sendMessage` / `sendApp` / `appEncode`
4. 不要再新增 `ProtocolFrame::buildMessage` 作为主发送路径（仅兼容/超大包兜底）


## 补充（整包 JSON 日志排查）

若通讯窗口仍出现「协议 JSON / 协议异常(整包JSON)」：

1. 确认已刷入本轮根节点/柜子固件（sendToUplink / uartHostSendRaw 已强制转二进制）
2. 正常 BIN 消息的 data 字段是 JSON 不算「协议 JSON 兼容」
3. 仅当 A5 帧内 payload 以 `{` 开头且无 B1 0F 信封时才会记异常
