# ESP-MESH 组网稳定性优化方案

## 背景与根因

实测监控（COM16 根节点 + COM10 柜子联合抓包）确认：CAB 不稳定的根因是 **ESP-MESH 链路层频繁 flap**（柜子反复 `PARENT_CONNECTED` -> 立即 `PARENT_DISCONNECTED reason=202 MESH_INTERNAL` / `reason=6 BEACON_TIMEOUT`），不是 panic、不是 boot loop、与上位机无关。

对照 Espressif 官方文档，定位到两类问题：

### 问题 1：违反官方 WiFi API 禁令（主因，导致 reason=202）
官方明确：**self-organized 启用后，`esp_mesh_start()` 和 `esp_mesh_stop()` 之间应用层不得调用任何 WiFi API**（disconnect/scan_stop/set_config 等），因为 Mesh 协议栈内部驱动 WiFi 状态机。

我们违反此禁令的三处：
- `disableStaHunting()`（mesh_comm.cpp:26-35）在 `esp_mesh_start()`（283行）**之后**被调用，内部调 `WiFi.disconnect` / `esp_wifi_disconnect` / `esp_wifi_set_config` / `esp_wifi_scan_stop`
  - 调用点 1：mesh_comm.cpp:304（Root 分支，start 之后）
  - 调用点 2：mesh_comm.cpp:319（Child 分支，start + `set_self_organized(true,true)` 之后）
- 主循环 STA 守卫（mesh_comm.cpp:600-617）每 10s 在 mesh 运行时调 `WiFi.setAutoReconnect(false)` / `esp_wifi_scan_stop()`，且 STA SSID 非空时还调 `esp_wifi_set_config` + `esp_wifi_disconnect`

这会打断 Mesh 协议栈的 WiFi 状态机，直接导致抓到的 `reason=202 MESH_INTERNAL` 反复断开。

**替代方案**：纯 Mesh 模式下 `cfg.router.ssid_len=0`（mesh_comm.cpp:189）已让协议栈不扫外部热点，根本不需要应用层干预 STA 状态。

### 问题 2：缺失稳定性参数（次因，导致 reason=6 BEACON_TIMEOUT）
- `esp_mesh_set_active_duty_cycle` 未调用，用默认 10（低占空比，beacon 易丢）
- `esp_mesh_set_send_block_time(500)`（mesh_comm.cpp:278）太短，官方建议环境差时 ≥5s

### 问题 3：recovery 逻辑可能加剧抖动
柜子 `rootResponseTimedOut` 后，60s 强制 `esp_mesh_disconnect()` + 重连（mesh_comm.cpp:674-685），可能打断 Mesh 协议栈的自愈过程。

## 改动清单

所有改动集中在 **2 个文件**：`esp32_firmware/common/mesh_comm.cpp` 和 `esp32_firmware/common/config_common.h`。根节点和柜子共用 `mesh_comm.cpp`，一次改动两边受益。

### 改动 1：移除 `disableStaHunting()` 函数及其所有调用（mesh_comm.cpp）

**删除函数定义**（mesh_comm.cpp:26-35）：
```cpp
// 整个 disableStaHunting() 函数删除
static void disableStaHunting() {
    WiFi.setAutoReconnect(false);
    WiFi.disconnect(false, true);
    wifi_config_t staCfg;
    memset(&staCfg, 0, sizeof(staCfg));
    esp_wifi_set_config(WIFI_IF_STA, &staCfg);
    esp_wifi_disconnect();
    esp_wifi_scan_stop();
}
```

**删除 Root 分支调用**（mesh_comm.cpp:301-306）：
```cpp
// 删除这两行
disableStaHunting();
Debug::println(F("[MESH] Root STA hunting disabled (pure mesh/USB)"));
```
保留注释说明为何不需要：`cfg.router.ssid_len=0` 已让协议栈不扫外部热点。

**删除 Child 分支调用**（mesh_comm.cpp:317-321）：
```cpp
// 删除这三行
if (s_pureMeshNoRouter || devCfg.wifi_ssid.length() == 0) {
    disableStaHunting();
    Debug::println(F("[MESH] Child STA hunting disabled (pure mesh)"));
}
```
同理，纯 Mesh 下 `ssid_len=0` 已足够。

### 改动 2：移除主循环 STA 守卫（mesh_comm.cpp:600-617）

**整块删除**：
```cpp
// 删除整个 if (s_pureMeshNoRouter && meshStarted) { ... } 块
if (s_pureMeshNoRouter && meshStarted) {
    static unsigned long lastStaGuard = 0;
    unsigned long nowGuard = millis();
    if (nowGuard - lastStaGuard >= 10000UL) {
        lastStaGuard = nowGuard;
        WiFi.setAutoReconnect(false);
        esp_wifi_scan_stop();
        wifi_config_t staCfg;
        if (esp_wifi_get_config(WIFI_IF_STA, &staCfg) == ESP_OK &&
            staCfg.sta.ssid[0] != 0) {
            memset(&staCfg, 0, sizeof(staCfg));
            esp_wifi_set_config(WIFI_IF_STA, &staCfg);
            esp_wifi_disconnect();
        }
    }
}
```

`WiFi.setAutoReconnect(false)` 已在 start 之前（mesh_comm.cpp:154）设过，不会丢失。`s_pureMeshNoRouter` 变量保留（start 之前的配置逻辑 191/196/233 仍用）。

### 改动 3：添加 `esp_mesh_set_active_duty_cycle(100)` 禁用 PS（mesh_comm.cpp）

在 `esp_mesh_start()`（283行）**之前**，`esp_mesh_set_ap_assoc_expire(120)`（262行）附近添加：
```cpp
// 柜子市电供电，禁用 Mesh 低功耗（dev_duty=100）。低占空比默认 10 会导致
// beacon 丢失 -> BEACON_TIMEOUT 频繁断开。根节点 duty 恒为 100，此处对根无副作用。
esp_mesh_set_active_duty_cycle(100, MESH_PS_DEVICE_DUTY_DEMAND);
```
位置：mesh_comm.cpp:262 之后、`esp_mesh_set_type`（270行）之前。

### 改动 4：放宽 `esp_mesh_set_send_block_time`（mesh_comm.cpp:278）

```cpp
// 原：esp_mesh_set_send_block_time(500);
// 改为：
// 官方建议环境差时 ≥5s，避免 esp_mesh_send 频繁超时导致 sendAppRaw failed
esp_mesh_set_send_block_time(5000);
```

### 改动 5：放宽 recovery 强制断开阈值（mesh_comm.cpp + config_common.h）

**config_common.h** 新增常量（放在 MESH_ROUTE_TIMEOUT_MS 附近）：
```cpp
// Root 应用层无响应时强制重关联的阈值。原 60s 偏激进，会打断 Mesh 协议栈自愈。
// 放宽到 120s，让协议栈有足够时间自行恢复 parent 关联。
#define MESH_FORCE_REASSOC_MS    120000UL
```

**mesh_comm.cpp:43** 原 `FORCE_REASSOC_AFTER_MS = 60000UL` 改为引用配置常量：
```cpp
// 原：static const unsigned long FORCE_REASSOC_AFTER_MS = 60000UL;
static const unsigned long FORCE_REASSOC_AFTER_MS = MESH_FORCE_REASSOC_MS;
```

**mesh_comm.cpp:674-685** 强制断开逻辑保留，但阈值放宽后触发频率降低。同时增加注释说明这是兜底，正常情况应靠协议栈自愈：
```cpp
// 兜底机制：仅当 Root 应用层长时间（120s）无响应、且 Mesh 协议栈自愈失败时，
// 才强制断开 parent 重关联。正常 flap 由协议栈自行处理，不进这里。
if (meshConnected &&
    now - rootUnreachableSince >= FORCE_REASSOC_AFTER_MS &&
    (lastForcedReconnectTime == 0 ||
     now - lastForcedReconnectTime >= FORCE_REASSOC_AFTER_MS)) {
    // ... 原逻辑不变
}
```

## 不改动的部分

- **`MESH_ROUTE_TIMEOUT_MS` 保持 30s**（你的选择）：靠修复 WiFi API 问题让 Mesh 稳定，心跳不再缺失，30s 足够。
- **`ap_assoc_expire` 保持 120s**：已远超官方建议的 30s，不是问题。
- **`fix_root(true)` 保持**：符合官方固定根节点建议。
- **`set_self_organized(true,true)` 保持**：符合官方自组织自愈建议。
- **心跳条件 `meshConnected` 保持**：Mesh 断开时不发心跳是合理的，靠协议栈快速重连解决。
- **`MESH_CHANNEL=6` 不改**：信道优化属于物理层，先修固件逻辑问题，信道是否要换待修完后再测。

## 验证方式

改完后重新编译烧录根节点和柜子，再跑我之前写的 `diag_stability.py`（根节点 90s）和 `diag_dual.py`（双端口 120s）：
- 期望：`PARENT_DISCONNECTED reason=202` 消失或大幅减少
- 期望：柜子 HEARTBEAT 稳定每 10s 到达根节点
- 期望：根节点 CAB 稳定显示 `1/1` 不再掉 0

如果改完后仍有 `reason=6 BEACON_TIMEOUT`，说明是 RF/信道问题，再考虑换信道或挪近柜子。

## 风险评估

- **改动 1/2（移除 WiFi API 调用）**：低风险。纯 Mesh 下 `ssid_len=0` 已是正确配置，应用层干预反而有害。最坏情况是某个边界场景下 STA 残留 SSID 触发扫描，但 `set_self_organized` 会接管，且 `WiFi.setAutoReconnect(false)` 已在 start 前设过。
- **改动 3（dev_duty=100）**：低风险。柜子市电供电，功耗无感。根节点 duty 恒为 100 无副作用。
- **改动 4（block_time 5s）**：低风险。最坏情况是 send 阻塞更久，但 `MESH_DATA_NONBLOCK` flag 已用，实际不会阻塞主循环。
- **改动 5（recovery 阈值 120s）**：低风险。只是让协议栈自愈时间更长，120s 仍是合理兜底。
